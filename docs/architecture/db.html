What gets saved, where

Data model

The schema is the constitution's data contract (§11) made durable. Storage splits by lifecycle: a read-only build corpus, one runtime DB, and a config file.

Two databases + one config file

profile.yaml static / monthly-frozen constants (§1, §3) — a FILE, not a table written by bootstrap + monthly recompute · human-editable · git-diffable baseline.db read-only historical corpus (3.5M records, 2019→2026) regenerated wholesale by build_db.py · NEVER opened at runtime │ derive constants → profile.yaml │ + seed trailing ~90 days ▼ app.db ─────────────────────────────────────────────── Alembic · WAL the ONLY database the running API reads or writes ┌─ INGEST (POST /sync) ─────────────────────────────────────────┐ │ records · workouts · workout_statistics · activity_summary │ │ raw HealthKit — mirrors baseline.db + uuid/origin · upsert │ └───────────────────────────┬──────────────────────────────────┘ ▼ recompute affected days on every sync ┌─ DERIVED (materialized cache) ──────────────────────────────┐ │ daily_metrics — 1 row/day: sleep · HRV · RHR · 30d mean+SD · │ │ zone-min · nutrition intake · body_weight · readiness · band │ │ → the 7/28d rollups (training + nutrition) sum over it │ └───────────────────────────────────────────────────────────────┘ ┌─ COACHING STATE ─────────────────────────────────────────────┐ │ checkins · strength_tests ← inputs (a few taps) │ │ plans · suggestions ← brain outputs / cache │ └───────────────────────────────────────────────────────────────┘
app.db = 9 tables. No profile table — those constants live in profile.yaml (§5). All timestamps are ISO-8601 TEXT carrying the actual offset HealthKit emits per sample (Europe/Sofia is +0200 in winter, +0300 in summer, plus travel); period keys (date, iso_week) derived through the Europe/Sofia tz database (DST-aware), never by assuming a fixed offset.

Ingest tables

Raw HealthKit, structurally mirroring baseline.db so the 90-day seed is a straight copy. Two additions: a unique uuid (idempotency) and an origin flag. Only whitelisted types are stored — now including dietary intake and body weight.

Indexes: UNIQUE(uuid) · (type, start_date) · (start_date). Write: INSERT … ON CONFLICT(uuid) DO NOTHING. Whitelisted types only. Activity / recovery: HR, HRV SDNN, RHR, sleep analysis, steps, active energy, basal energy, PhysicalEffort/METs, VO₂max, body mass (body weight), running cadence & dynamics. Dietary intake (NEW — logged in a 3rd-party app that writes to HealthKit): dietary_energy_consumed, protein, carbohydrates, fat (total), fiber, sodium, water → power the nutrition intake-vs-target adherence.
Body weight comes from HealthKit (body_mass records) like every other measurement — not manual. The latest body_mass is materialized into daily_metrics.body_weight and is the single live-weight source for TDEE/macros — there is no manual weight field on the check-in, so no dedup ambiguity.

Materialized cache

Derived · daily_metrics

One row per day, recomputed whenever that day's source data changes (on sync). The single source for the 7/28-day rollups (windowed sums, now covering training and nutrition adherence) and the rolling readiness baselines.

daily_metrics date PK

ColumnTypeNotes

readiness_score / band are also snapshotted onto the suggestions row for that date, but daily_metrics is the canonical per-day series.
hard_day — the corroborated rule. 1 if ANY of the day's workouts is hard, decided per workout in this order: (1) duration ≥ 90 min — unconditional, never gated; (2) confirmed by either intensity signal, whatever the activity type — a valid workouts.effort_score ≥ 7 on a session of ≥ 20 min, or ≥ 15 minutes of z4+z5 credited inside that workout's own start–end window (minutes earned elsewhere in the day, or by another session, never count); (3) otherwise the activity-type fallback — boxing / high_intensity_interval_training / kickboxing / martial_arts — but ONLY when both signals are absent. "Absent" means untrustworthy, not merely null: an effort_score outside 1–10 is treated exactly as NULL, and the zone signal counts as present only when credited in-window HR reaches 50 % of the workout's duration; promotion by z4+z5 is deliberately not coverage-gated. Always a real 0/1, never null. Constants live in app/services/daily_metrics_engine.py; rationale in docs/artifacts/plans/corroborated-hard-day/DECISIONS.md.

05
Constants · a file, not a table

profile.yaml

The single source of truth for every numeric constant — athlete profile (§1), zones (§3), nutrition (§7): set once, refreshed monthly (§10). HEALTH-CONSITTUTION.md is a Jinja2 template rendered from it, so the rulebook can't drift. A YAML file is the better home — human-editable, git-diffable. Live/derived look-alikes stay in the DB.

What's a constant vs. what's live

file profile.yaml · static / monthly-frozen
  • age, sex, height_cm, goal_weight_kg
  • max_hr, rhr_baseline (zone anchor)
  • easy_hr_cap (146), cadence_target_spm, cadence_current_spm
  • zones — Z1–Z5 bpm bounds
  • nutrition — activity factor, deficit %, protein/fat g/kg, carb multipliers, hydration, fiber
DB live / derived
  • current weight → latest body_mass (HealthKit) → daily_metrics.body_weight
  • 30d HRV mean+SD, 30d RHR mean → daily_metrics
  • per-day sleep / zone-min / readiness → daily_metrics
  • per-day nutrition intake → daily_metrics
rhr_baseline/hrv_baseline in the file are the monthly-frozen anchors used to derive zones. The readiness score reads the live rolling values from daily_metrics, not these — one rolling baseline, not two competing ones.

Who writes what · bootstrap

Write paths & bootstrap

Each endpoint owns a clear slice of the schema; an offline build step seeds the runtime DB before the first request.

Who writes what

TriggerWrites
POST /syncrecords / workouts / workout_statistics (upsert by uuid), activity_summary (by date), checkins (by date), strength_tests (by week) → then recompute daily_metrics for affected dates.
POST /brief/weeklyplans; may rewrite profile.yaml when constants are stale (§10).
POST /brief/dailysuggestions (+ readiness_score/band back to daily_metrics).

Bootstrap — one-time, at deploy

baseline.db ──(offline build step)──▶ app.db + profile.yaml 1. derive constants from baseline.db ──▶ write profile.yaml 2. copy trailing ~90 days of whitelisted samples into the ingest tables with origin = 'seed' └▶ first /brief/weekly has valid 7/28-day rollups & 30-day baselines on day one
After bootstrap, app.db grows from /sync forward and baseline.db is never consulted again.

Why it's shaped this way

Decisions & open items

The eight forks we resolved, and the two details still to lock before the first migration.

Decided

#DecisionWhy
1Two DBs, split by lifecyclebuild_db.py does DROP TABLE … every run; durable state can't live in a regenerable artifact.
2Ingest = raw records, mirroring baseline.db (+ uuid/origin)trivial 90-day seed; same aggregate queries over both DBs; least divergence.
3daily_metrics materialized (not inline)speed, reproducibility, debuggable day-level history; rollups = windowed sums.
4Two brief tables (plans + suggestions)payloads differ (weekly plan vs daily session + readiness/gate); shared columns would sit empty.
5Constants in profile.yaml, not a tableconfig-shaped, monthly-frozen, human-editable, git-versioned; live weight + rolling baselines stay in the DB.
6profile.yaml is the single source; the constitution is a Jinja2 templatenumbers exist in exactly one place. HEALTH-CONSITTUTION.md's {{ … }} placeholders render from profile.yaml, so the rulebook can't drift. §10 recompute rewrites profile.yaml only. (Resolves the former drift open-item.)
7Check-in is objective-only + single GI booleanreadiness is physiological (§6.1); dropped energy/soreness/motivation and granular GI; kept gi_symptoms/illness/knee_pain only. Knee is 0–10 (0 = none).
8Dietary intake and body weight come from HealthKitfood is logged in a 3rd-party app → HealthKit; weight is a body_mass record. Both ingest as records (closing the nutrition loop). Latest body_mass → daily_metrics.body_weight is the single live-weight source — no manual field, no dedup.

Open items (defaults proposed, not locked)

  • Seed↔sync overlap. Seeded rows (origin='seed', uuid=NULL) can overlap the first live sync's date range. Proposed: 'sync' rows are authoritative; a one-time reconciliation drops 'seed' rows for any day fully covered by synced data. needs a decision
  • Type whitelist exact list. The activity + dietary types are sketched in §1; finalize the precise HK…Identifier set (incl. HKQuantityTypeIdentifierDietary*) before the first migration.
