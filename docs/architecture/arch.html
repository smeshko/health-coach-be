Components

One synchronous FastAPI process over a SQLite file, orchestrating a node workflow that calls Claude.

Stack note — what we keep vs drop from the GenAI Launchpad. This backend builds on Datalumina's Launchpad boilerplate but uses only its FastAPI app, the core/ workflow primitives (Node/RouterNode/AgentNode/TaskContext), PydanticAI, Jinja2, and Alembic. The Launchpad's Postgres/pgvector, Celery, Redis, Supabase, streaming, and vecs/RAG are not used — single-user scale needs none of it, so the database/ layer is rewritten for SQLite and those deps are dropped.

Deployment & access

  • Deploy — one uvicorn process + one app.db file; optional Docker (a single api container).
  • Backup — litestream streams app.db's WAL to object storage continuously, so the one durable file survives disk loss.
  • Access — one long-lived API token over HTTPS, on a private network / Tailscale.

Structure

Computation & judgment

The system separates deterministic computation from LLM judgment; the node model expresses the boundary. The LLM performs no arithmetic.

The split

code Deterministic · Node + services/
  • HR zones (§3)
  • readiness score (§6.1)
  • 7/28-day rolling aggregates
  • HRV/RHR 30-day baselines
  • macros / TDEE (§7)
  • ≤10%/wk volume ramp (§9)
Claude Judgment · AgentNode
  • pick sessions from the pool
  • sequence the week
  • tune today's session
  • write the rationale
  • within budgets & flags only
pre-computed numbers + flags → fed to the brain as context

The training-readiness safety gate

SafetyGateRouter
any flag TRUE → REST
A RouterNode short-circuits to REST / active-recovery before the LLM is consulted. It enforces training auto-regulation only (GI symptoms / illness / knee / sleep / HRV-RHR). The §2 medical conditions are LLM context (system prompt), not a code-enforced layer — this is a fitness app, not a medical device.

Bootstrap (one-time, at deploy): a build step (a) freezes the derived constants into profile.yaml, and (b) copies the trailing ~90 days of relevant samples from baseline.db into app.db's ingest tables — so the first /brief/weekly has valid 7/28-day rollups and 30-day HRV/RHR baselines on day one. After that, app.db grows from /sync forward and baseline.db is no longer consulted.

04
How requests move

Request flows

Sync before brief — the readiness score and safety gate need last night's sleep, this morning's HRV, and the check-in to be stored first.

App-open sequence

1. user fills the daily check-in (GI symptoms / illness / knee) 2. POST /sync push HealthKit + check-in [+ weekly test] ← must be first 3. POST /brief/daily generates off the data just synced 4. if new ISO week → POST /brief/weekly

Get-or-generate

Keyed by period. The first request for a day/week generates (one LLM call); subsequent requests serve the cache.

POST /brief/daily: s = lookup(date = today) return s if exists else run DAILY_ADJUSTER → persist → return POST /brief/weekly: p = lookup(week = current_iso_week) return p if exists else run WEEKLY_PLANNER → persist → return
  • Enforced by a unique constraint on (brief_type, period_key).
  • ?refresh=true forces one regeneration (e.g. the check-in arrived late).
  • The morning brief, generated off this-morning HRV, deliberately stays stable all day.

Period key & timezone

Timestamps are stored with the actual UTC offset HealthKit emits per sample (Europe/Sofia +02:00 winter / +03:00 summer; varies with travel), not a hard-coded +0300. Period keys (date, iso_week) are derived via the Europe/Sofia tz database (DST-aware), so they track DST and travel correctly. Don't assume a fixed offset anywhere — always resolve "today" / "this week" through the tz database.

Effort / RPE

The app reads each workout's WorkoutEffortScore (RPE 1–10) from HealthKit and sends it in /sync; the first sync backfills available scores. Used when present. Auto-estimated PhysicalEffort (METs, 523k samples) is always available as an HR-independent intensity proxy.
