Overview

Ship the camelCase POST /sync request/response Pydantic models (eight of them) plus a shared wire-level type-whitelist filter that reuses E4's app/core/healthkit.py — a faithful field-for-field transcription of MODELS.md "POST /sync" + "Enums", not a design. Models + filter only; the route, upsert, and recompute are E5·P2 / E5·P3.

Goal

This phase ships the wire models + the whitelist filter only. It does not add the POST /sync route, the idempotent upsert, or the SyncResponse count derivation (E5·P2), nor the check-in / strength-test upsert + daily_metrics recompute (E5·P3). Pure Pydantic models + one pure-Python filter.
  • Epic — E5 — Sync / Ingest (POST /sync), phase P1 (first of three). Source of truth: epics/E05-sync-ingest.md (§1 summary; §2 R1 camelCase wire models / R2 RecordType + quantity/category / R3 whitelist / R7 objective-only check-in; §3 E5·P1; §4 acceptance; §6 validation; §7 out-of-scope).
  • Grounded in — MODELS.md "Conventions" (camelCase wire / snake_case Python via alias_generator; "Nulls vs absent"), "Enums → RecordType" (the 24-value list incl. seven dietary_* and body_mass), and "POST /sync" (the eight models field-for-field); DB.md §1 (ingest tables; "only the whitelisted types … are stored"; body_mass is the single live-weight source — no body-weight field on the check-in).
  • Depends on — E1·P1 (app/api/schemas/base.py CamelModel — alias_generator=to_camel, populate_by_name=True, serialize_by_alias=True; the T | None = None null-vs-absent convention) and E4·P3 (app/core/healthkit.py — the finalized HK…Identifier whitelist WHITELISTED_TYPES + is_whitelisted, shared at runtime).
  • Consumers — E5·P2's /sync route parses a SyncRequest, calls filter_whitelisted_records before the upsert, and returns a SyncResponse (camelCase JSON for free via serialize_by_alias=True).

Scope vs Out-of-Scope

In scope this phase
  • app/api/schemas/sync.py — all eight /sync wire models, each inheriting the E1·P1 CamelModel base (wire camelCase, Python snake_case, model_dump_json() emits camelCase with no by_alias=True).
  • RecordType(str, enum.Enum) — the exact MODELS "Enums" 24 snake_case values (incl. seven dietary_* + body_mass).
  • HealthRecord — both quantity (value+unit) and category (category) samples; optionals T | None = None.
  • The other seven: WorkoutStat, Workout, ActivitySummary, DailyCheckin, StrengthTest, SyncRequest, SyncResponse.
  • app/core/healthkit.py — extended: RECORD_TYPE_TO_HK bridge, is_record_type_whitelisted, filter_whitelisted_records (pure, derives membership from E4's frozenset).
  • Tests — tests/api/schemas/test_sync_models.py + extend tests/core/test_healthkit.py.
Out of scope later epics
  • The POST /sync route, idempotent upsert, SyncResponse count derivation — E5·P2 (model exists here; not populated from DB writes).
  • Check-in / strength-test upsert, ISO-week derivation, daily_metrics recompute fan-out — E5·P3.
  • The records/workouts/activity_summary/checkins/strength_tests SQLAlchemy tables — E2·P2 / E2·P3 (maps onto them; no ORM/migrations).
  • Defining the HK…Identifier whitelist set itself — E4·P3; this phase reuses it, adds only the bridge + filter, alters nothing.
  • Auth on /sync (unauthorized envelope) — bearer dep is E1·P2, wired in E5·P2. No endpoint here, so no auth here.
  • Dropped stack — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/vecs.

Research summary

The /sync wire contract is fully specified — this phase is transcription, not design. MODELS.md "POST /sync" pins eight models with camelCase field names (Swift Codable-friendly), Python snake_case behind the E1·P1 CamelModel alias generator. The one genuine decision is the bridge (RECORD_TYPE_TO_HK + is_record_type_whitelisted) that derives wire-type acceptance from the existing frozenset, keeping a single source of truth (DB.md §1 "only the whitelisted types … are stored"). HealthRecord is the one model with real shape logic — it carries both quantity and category samples, so those fields are all optional. DailyCheckin is objective-only (weight arrives as a body_mass record). Timestamps are datetime carrying the device offset; dates are datetime.date (YYYY-MM-DD).
