Local dev runner (justfile)

Ship a repo-root backend/justfile that makes local dev turnkey without Docker — wrapping the E1·P1 uvicorn entry point and forward-declaring the migrate/seed/bootstrap recipes that light up as E2/E4 land.

Goal

Make local dev turnkey: a backend/justfile (plus a .env bootstrap and a README "Local development" section) that boots the E1 scaffold today with no Docker, wrapping the E1·P1 uv run uvicorn app.main:app entry point and forward-declaring the migrate/seed/bootstrap recipes for E2/E4.

Epic context

  • Epic E1 — Foundation & API Skeleton, phase P4 (Local dev runner). Source of truth: epics/E01-foundation.md §3 "E1·P4" + §4 acceptance.
  • Grounded in ARCHITECTURE.md §1 — a single synchronous uvicorn process; Docker/litestream are optional deployment (E12), not local dev.
  • Builds on E1·P1 (the uv project + uv run uvicorn app.main:app entry point + canonical .env.example) and E1·P2 (so just run serves GET /health).
  • Forward recipes target E2·P1 (uv run alembic upgrade head) and E4 (scripts/build_db.py, scripts/derive_constants.py, scripts/seed_app_db.py).
  • Status: draft · Risk: small · 3 implementation tasks + 1 final-validation task.

Scope vs Out-of-Scope

In scope this phase
  • A justfile at backend/justfile with a _default recipe (@just --list) so bare just lists every recipe.
  • Core recipes that work today: install → uv sync, run → uv run uvicorn app.main:app --reload, test → uv run pytest, lint → uv run ruff check ., fmt → uv run ruff format ..
  • Forward-declared lifecycle recipes: migrate, seed, bootstrap, db-reset — authored now, calling the correct future E2/E4 commands.
  • .env handling: an env recipe that copies .env.example → .env only when .env is missing (never clobber).
  • README "Local development" section with two separated flows (E1-now boot path + post-E2/E4 full flow) and a per-recipe reference.
Out of scope later phases
  • Docker / litestream / migrate-on-startup — deployment-only, lives in E12·P2. No Dockerfile, compose file, or startup migration.
  • The app/DB code the forward recipes call: Alembic config (E2·P1) and bootstrap scripts (E4·P1/P2/P3) are authored in their own phases.
  • Editing .env.example content beyond what E1·P1 ships (E1·P1 owns it; append only a genuinely-required var).
  • CI wiring, pre-commit hooks, task runners other than just.
NO DOCKER LOCALLYLocal dev is just uv + just — no Dockerfile/compose/litestream/startup-migration (ARCHITECTURE §1; deferred to E12·P2).

Research summary

Why local dev needs neither Docker nor litestream, and where the forward commands come from.

  • Runtime is one synchronous Python 3.13 uvicorn process with an app.db SQLite file (ARCHITECTURE §1). Docker is "optional (a single api container)" and litestream is the deployment backup path — both deferred to E12.
  • Canonical entry point set in E1·P1 is uv run uvicorn app.main:app; this phase's run recipe wraps it with --reload.
  • Forward commands mirror later phases: E2·P1 uses uv run alembic upgrade head against app.db (URL from settings.app_db_path); E4 defines scripts/build_db.py (E4·P1), scripts/derive_constants.py (E4·P2), scripts/seed_app_db.py (E4·P3).
  • Gitignored artifacts: app.db* (*.db/*.db-wal/*.db-shm) and .env are gitignored, so db-reset only ever deletes untracked files and a real .env is never committed. E1·P1 owns the committed .env.example.

db-reset safety design

A single shebang Bash block — two operational subtleties make it one shell, not multiple recipe lines.

#!/usr/bin/env bash set -euo pipefail DB="${APP_DB_PATH-app.db}" # unset → app.db; explicit-empty stays empty [ -n "$DB" ] || { echo "db-reset: APP_DB_PATH is empty; refusing" >&2; exit 1; } case "$(basename "$DB")" in baseline.db) echo "db-reset: refusing baseline.db" >&2; exit 1;; esac rm -f -- "$DB" "$DB-wal" "$DB-shm" just migrate
  • One shell block — just runs each plain recipe line in its own process, so DB=… on one line would not survive to the guard/rm; a shebang block keeps them together.
  • ${APP_DB_PATH-app.db} not :- — an explicitly empty APP_DB_PATH stays empty and is caught by the [ -z ] refusal rather than silently collapsing to app.db.
  • Explicit siblings, never a glob — rm -f -- "$DB" "$DB-wal" "$DB-shm" (-- stops option parsing). All three are gitignored, so nothing tracked is ever touched.
  • Refuses baseline.db — a read-only build input (ARCHITECTURE §3) is never deleted.

Acceptance criteria

The phase's contract — every box must be green before E1·P4 is done. Final validation (page 05) maps concrete checks back to each of these.

Acceptance criteria

  • ☐ AC1 — bare just lists recipes — just with no args and just --list both show: install, run, test, lint, fmt, migrate, seed, bootstrap, db-reset, env (the _default recipe runs @just --list).
  • ☐ AC2 — core recipes work against the E1 scaffold now — just install runs uv sync; just lint → uv run ruff check .; just test → uv run pytest; just fmt → uv run ruff format .; just run → uv run uvicorn app.main:app --reload (serving /health from E1·P2). Verified by --show/-n and actual runs.
  • ☐ AC3 — forward recipes invoke the correct future commands — --show migrate → uv run alembic upgrade head; --show seed → the E4 scripts (build_db.py/derive_constants.py/seed_app_db.py); --show bootstrap chains install→migrate→seed; --show db-reset removes app.db/-wal/-shm then re-migrates.
  • ☐ AC4 — .env bootstrap is non-clobbering — just env copies .env.example → .env when absent and is a no-op when .env exists; a real .env is never committed (gitignored).
  • ☐ AC5 — README "Local development" section — exists with two separated flows: the E1-now boot path (install → env/set .env → run → curl /health) that completes today, and the post-E2/E4 full flow inserting migrate/bootstrap; lists each recipe with one line and notes which depend on E2/E4.
  • ☐ AC6 — no Docker/litestream/migrate-on-startup introduced — no Dockerfile/compose/litestream files; the justfile contains no docker/litestream references (grep is empty).
