E2 · P3 · orientation

Derived & coaching-state tables

The five non-ingest tables that complete app.db's 9-table set: one derived per-day cache plus four coaching-state tables — schema only, no data, no write path.

Goal

Goal: define five SQLAlchemy models — one derived (daily_metrics) and four coaching-state (checkins, strength_tests, plans, suggestions) — under app/database/models/, plus one Alembic migration that creates them with the exact UNIQUE/PK constraints from DB.md §2–§4. Completing this brings app.db to its full 9 tables with no profile table — schema only, no data.

  • Dropped stack: Postgres/pgvector, Celery, Redis, Supabase, RAG/vecs

The five tables at a glance

One derived materialized cache and four coaching-state tables. The load-bearing constraints are the cache keys: UNIQUE(iso_week) on plans/strength_tests and UNIQUE(date) on suggestions.

tablekindprimary keycache / period key
daily_metricsderiveddate TEXT PK (NOT NULL)one row per Europe/Sofia day
checkinsstate · inputdate TEXT PK (NOT NULL)upsert by date
strength_testsstate · inputid INTEGER PKUNIQUE(iso_week)
plansstate · outputid INTEGER PKUNIQUE(iso_week)
suggestionsstate · outputid INTEGER PKUNIQUE(date)
No inter-table FKs: none of the five tables references another, so the migration downgrade() drop order is unconstrained. E2·P1's connect listener (PRAGMA foreign_keys=ON, WAL) and naming_convention (uq/pk/ix) still apply, so the autogenerated migration is deterministic and constraint names are assertable.

Key decisions

decisionrationale
One module per table, re-exported from models/__init__.pyContinues the E2·P2 pattern — each table reviewable in isolation; one import registers all nine on the shared Base.metadata for autogenerate.
daily_metrics.date / checkins.date are TEXT PKs declared primary_key=True, nullable=FalseDB.md §2/§3 make date the PK. SQLite's non-WITHOUT ROWID TEXT PK is NULL-tolerant, so the explicit nullable=False stops multiple date=NULL rows silently breaking per-day uniqueness (E2·P2 round-1 #1).
strength_tests/plans/suggestions keep a surrogate id PK + a separate UNIQUE period columnDB.md §3/§4 specify id PK + iso_week/date UNIQUE. The id is row identity; the period column is the cache key the get-or-generate flow looks up.
readiness_score/band (daily_metrics) and gate_reason (suggestions) are nullable=TrueA sync-time row created before any brief must persist with these NULL (DB.md §2/§4); the daily brief fills them later (E11).
payload is NOT NULL on plans/suggestions; inputs_snapshot/rationale nullableA cached brief without its payload is meaningless (DB.md §4); the snapshots are reproducibility/explanation fields that may be absent.
JSON columns (payload, inputs_snapshot) stored as Text, not a JSON typeSQLite has no native JSON storage (JSON1 operates on TEXT); the contract is JSON-as-TEXT — keeps the migration portable and the stored bytes verbatim.
All timestamps (computed_at/created_at/updated_at) are Text, not DATETIMEThe contract stores ISO-8601 TEXT carrying the per-sample offset; nothing normalizes the offset away (DB.md §0; E2·P1).
hard_day/gi_symptoms/illness/safety_gate_tripped are Integer (0/1); knee_pain Integer (0–10)SQLite has no native boolean; ranges are application invariants enforced at the write layer (E5/E11), not DB CHECK constraints — the schema stays a faithful mirror of DB.md.
One migration for all five tables, authored complete in TASK-003They land in one cohesive PR; a single revision keeps the chain linear and the up/down round-trip atomic. TASK-001/002 add only models (validated via create_all) and no revision — removing the partial/stale-revision hazard.
No profile table; a positive 9-table assertion guards itConstants live in profile.yaml (E3), not the DB. A test asserts the user-table set is exactly the 9 named tables and profile is absent.

Risks & mitigations

riskmitigation
A UNIQUE(iso_week)/UNIQUE(date) cache key dropped or mis-named in autogenerate → two briefs per period coexistTests introspect the migrated DB (PRAGMA index_list/index_info, sqlite_master) and assert each UNIQUE index; duplicate-insert tests assert IntegrityError.
readiness_score/band/gate_reason made NOT NULL by mistake → a sync-time row can't insertModels declare them nullable=True; a test inserts rows leaving them unset and reads NULL back.
A date TEXT PK left NULL-tolerant → multiple date=NULL rows break per-day uniquenessDeclare primary_key=True, nullable=False; a test asserts PRAGMA table_info reports pk=1/notnull=1 and a date=NULL insert raises IntegrityError.
payload accidentally nullable → a cached brief with no bodyDeclare payload nullable=False; a test asserts notnull=1 and a NULL-payload insert raises IntegrityError.
A stray/extra table or a reintroduced profile table → epic R3 violatedA test asserts the user-table set after upgrade head is exactly the 9 named tables and 'profile' not in it.
Wrong column type (e.g. steps stored REAL, a timestamp/JSON as non-TEXT)A test reads PRAGMA table_info per table and asserts the declared SQLite affinity (INTEGER / REAL / TEXT).
Round-trip fails on the migration chainupgrade head→downgrade base→upgrade head test; down_revision points at the E2·P2 ingest head so the chain stays linear.
Models not registered on Base.metadata → autogenerate emits an empty migrationmodels/__init__.py imports all five; a test asserts the five table names are in Base.metadata.tables.
A partial/stale state_tables revision treated as current on a durable DBNo revision is created until TASK-003; the single revision is authored complete in one shot. Final validation also runs a migration↔metadata parity check (empty compare_metadata diff).
Migration accidentally targets baseline.db / leaks a dropped-stack depReuse E2·P1's alembic/env.py (settings-owned URL); grep -rn baseline alembic and the dropped-stack grep stay empty.
