Overview

An offline build step (scripts/derive_constants.py + scripts/compute_zones.py) that reads the read-only baseline.db, derives the athlete / threshold / zone / nutrition constants, and writes a profile.yaml that passes the E3·P1 Profile validator verbatim, with meta stamped.

Goal

This is an OFFLINE BUILD STEP, not FastAPI runtime. It lives in scripts/ (outside app/), opens baseline.db read-only, and its only app/ import is app.core.profile (the E3·P1 validator). baseline.db is never opened at runtime (ARCHITECTURE §6 / DB.md §0).
  • What it does — reads the read-only baseline.db (E4·P1), derives the data / computed / config constants, assembles the five-section dict, validates it via the E3·P1 Profile before writing, then dumps profile.yaml with meta stamped.
  • Epic — E4 — Baseline ETL & Bootstrap, phase P2. Source of truth: epics/E04-baseline-bootstrap.md (§1, §2 R2, §3 E4·P2, §4, §6, §7).
  • Grounded in — DB.md §5 (the profile.yaml five-section block — athlete/thresholds/zones/nutrition/meta, every field, the caps, the static-vs-live split + footnote ¹), DB.md §6 (bootstrap write path), DB.md §0/§1 (baseline.db raw shape, TEXT timestamps, Europe/Sofia period keys), ARCHITECTURE §3/§6 (Bootstrap; deterministic computations), and HEALTH-CONSITTUTION §3 (zones = %max-HR; Maffetone easy cap) + §7 (nutrition constants).
  • Depends on — E3·P1 (app.core.profile — the Profile schema/validator this output must pass) and E4·P1 (baseline.db — the corpus this reads).

Three sources of the constants

Data-derived from records
  • max_hr — bounded max of HeartRate samples across the whole corpus ("observed boxing peaks", constitution §3); spike-clamped by HR_FLOOR/HR_CEILING.
  • rhr_baseline — median of in-window RestingHeartRate (the monthly zone anchor, DB.md §5 ¹).
  • hrv_baseline_ms — median of in-window HeartRateVariabilitySDNN (ms; informational).
  • cadence_current_spm — robust median of in-window running-cadence (CADENCE_TYPE).
Computed + config anchors not fitted
  • Computed — easy_hr_cap = 180 − age (Maffetone, constitution §3).
  • Computed — zones via compute_zones(max_hr, rhr_baseline) (%max-HR).
  • Config anchors — the athlete block (age/sex/height_cm/goal_weight_kg), cadence_target_spm (ramp END target), and the entire nutrition block (DB.md §5 / constitution §7 — clinician/profile constants, injectable).
RECENT WINDOWRolling anchors (rhr / hrv / cadence) use the trailing RECENT_DAYS ≈ 90 days from the latest sample. max_hr is corpus-wide — windowing it could miss the true peak.

Scope vs Out-of-Scope

In scope this phase
  • scripts/compute_zones.py — pure, I/O-free compute_zones(max_hr, rhr) -> dict[str, tuple[int,int]] returning {"z1": (lo,hi), …, "z5": (lo,hi)} as %max-HR bands with shared integer edges.
  • scripts/derive_constants.py — the offline derivation: open baseline.db read-only, derive the data thresholds, compute easy_hr_cap + zones, carry the config anchors, validate via Profile, stamp meta, write profile.yaml.
  • tests/scripts/test_compute_zones.py — the §5-exact case + the contiguity/monotonicity invariants.
  • tests/scripts/test_derive_constants.py — synthetic baseline.db in tmp_path → derive → round-trip + meta + caps + determinism assertions.
Out of scope other phases
  • Building baseline.db (the export.xml → corpus ETL) — E4·P1 (build_db.py); this phase only reads the corpus.
  • The Profile schema / loader / validator itself — E3·P1 (app/core/profile.py); reused here, never modified.
  • The 90-day seed + seed↔sync reconciliation — E4·P3.
  • The monthly RecomputeConstants rewrite + the cadence +5/2–3wk ramp — E8·P5 / §10; this phase writes only the first month's values.
  • Consuming the constants (macro/TDEE engine, HR-zone bucketing, constitution render) — downstream readers (E8 / E3·P2 / E9).
  • daily_metrics / live-derived values (current weight, 30d HRV/RHR rolling baselines) — live in the DB, not written to profile.yaml (DB.md §5 ¹).
  • Dropped stack — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/vecs (ARCHITECTURE §1).

Research summary

  • profile.yaml is the E3 schema — five sections (athlete/thresholds/zones/nutrition/meta) with hard caps and zones that must be monotonic + contiguous; E3·P1 already encodes all of this in the Profile validator. The output must pass it verbatim.
  • The E3·P1 constraints this output must satisfy — thresholds.max_hr > thresholds.rhr_baseline; zones monotonic and contiguous (low < high, lows strictly increasing, zN.high == z(N+1).low); deficit_pct ≤ 0.20, protein_g_per_kg ≤ 2.0, fat_g_per_kg_low ≤ fat_g_per_kg_high; carbs_g_per_kg requires all five keys; extra="forbid" on every section; meta.computed_at is a datetime.date.
  • Bootstrap is offline + deterministic — derives the constants from the read-only baseline.db and writes the file; baseline.db is never opened at runtime, so the script lives in scripts/, not app/ (DB.md §6; ARCHITECTURE §3/§6).
  • Zones = % of max HR — verified at max_hr=192: round(.50·192)=96, round(.65·192)=125, round(.78·192)=150, round(.87·192)=167, round(.92·192)=177, 1.00·192=192 → exactly the §5 block. Pure %max-HR with one rounding pass reproduces the canonical example.
  • The constant split — max_hr/rhr_baseline/hrv_baseline_ms/cadence_current are data-derived from records (by HK type); easy_hr_cap = 180 − age is Maffetone-computed; the athlete block, cadence_target_spm, and the whole nutrition block are config anchors (constitution §7), carried through, not fitted.
  • baseline.db raw shape — records(type, unit, value, value_text, source_name, source_version, device, creation_date, start_date, end_date), no uuid/origin, TEXT timestamps verbatim as Apple emits ("2016-05-18 16:45:52 +0300"). HR/HRV/RHR/cadence are all records rows distinguished by type.

task 001 · zone math

compute_zones from maxHR and RHR

A pure, I/O-free compute_zones(max_hr, rhr) that returns the Z1–Z5 bpm bounds as %max-HR bands with shared integer edges, so the result is contiguous + monotonic by construction and passes the E3·P1 Zones validator for any max_hr.

Commit: feat(scripts): add compute_zones (%max-HR Z1–Z5 bpm bounds) · Depends on: none. Lands the zone-math layer as a pure function (no DB, no I/O) so TASK-002 can call it from derive_constants.

Files

pathchangewhat
scripts/compute_zones.pynewZONE_EDGES = (0.50, 0.65, 0.78, 0.87, 0.92, 1.00) (constitution §3: Z1 50–65%, Z2 65–78%, Z3 78–87%, Z4 87–92%, Z5 92–100%); compute_zones(max_hr, rhr) -> dict[str, tuple[int,int]] rounds the six shared edges once (edges = [round(pct * max_hr) …]) and pairs adjacent edges → z1=(e0,e1) … z5=(e4,e5). rhr is a named param, unused in the cutpoint math.
tests/scripts/test_compute_zones.pynewThe §5-exact case + the contiguity/monotonicity invariants over several max_hr values + an rhr-irrelevance test.

Acceptance

  • compute_zones(192, 58) == {"z1": (96,125), "z2": (125,150), "z3": (150,167), "z4": (167,177), "z5": (177,192)} — the DB.md §5 example verbatim.
  • For a range of max_hr (e.g. 170, 185, 200, 210): every zN.high == z(N+1).low (contiguous), each low < high, and the lows strictly increasing (monotonic) — the E3·P1 Zones validator's invariants.
  • z1.low == round(0.50 * max_hr) and z5.high == max_hr (the band spans 50%→100% of max).
  • Changing rhr does not change the returned bounds (rhr is not in the cutpoint math).

Shared-edge construction

# round the six band edges ONCE, then pair adjacent edges edges = [round(pct * max_hr) for pct in ZONE_EDGES] # e0..e5 # at max_hr=192 → [96, 125, 150, 167, 177, 192] { "z1": (e0, e1), "z2": (e1, e2), "z3": (e2, e3), "z4": (e3, e4), "z5": (e4, e5) } # zN.high IS the same int as z(N+1).low → contiguous by construction
Watch out: never round a zone's low and high independently — that can produce z1.high=124, z2.low=125 and the E3·P1 contiguity validator would reject it. The whole point is one rounding pass over the shared edges.
