Overview

Finish E4: ship the finalized HealthKit type whitelist (shared with E5), an offline 90-day seed that copies the trailing window of whitelisted samples from baseline.db into app.db with origin='seed', and a one-time seed↔sync reconciliation — so the first /brief/weekly has valid rollups on day one.

Goal

This is the final E4 phase. It ships three deliverables: app/core/healthkit.py (the type whitelist, the one runtime-shared piece), scripts/seed_app_db.py (the offline seed), and scripts/reconcile_seed.py (the one-time reconciliation). The seed gives the brain its trailing-90-day history so the first weekly brief has valid 7/28-day rollups and 30-day HRV/RHR baselines. baseline.db is never opened at runtime.
  • Epic — E4 — Baseline ETL & Bootstrap, phase P3. Source of truth: epics/E04-baseline-bootstrap.md (§1, §2 R3 seed / R4 whitelist / R5 reconciliation, §3 E4·P3, §4 acceptance, §6 validation, §7 out-of-scope).
  • Grounded in — DB.md §0 (two-DB split; ISO-8601 TEXT timestamps; Europe/Sofia period keys), §1 (the four ingest tables — the uuid/origin additions, the date_components→date rename, the whitelisted-type list incl. dietary + body_mass), §6 (bootstrap: copy the trailing ~90 days with origin='seed'), §7 (the two open items this phase resolves — the exact whitelist set + the seed↔sync rule); ARCHITECTURE.md §3 (Bootstrap) and §6 (baseline.db is a build input, never opened at runtime).
  • Resolves two open items — DB.md §7 left both the exact whitelist set and the seed↔sync reconciliation rule as "Needs a decision"; this phase decides and implements both.
  • Depends on — E4·P1 (baseline.db raw corpus), E2·P2 (the four app.db ingest models + their ingest_tables Alembic revision — the seed's target schema), and E2·P1 (app/core/time.py Europe/Sofia period-key helpers; app/database/engine.py).

Scope vs Out-of-Scope

In scope this phase
  • app/core/healthkit.py — the finalized WHITELISTED_TYPES frozenset (activity/recovery + dietary + body_mass), named subsets, CADENCE_TYPE, is_whitelisted(). Pure data, no DB/IO.
  • scripts/seed_app_db.py — copy the trailing ~90 Sofia days of whitelisted samples into the four ingest tables with uuid=NULL, origin='seed', the date_components→date rename; idempotent; CLI --baseline/--app-db/--now/--days.
  • scripts/reconcile_seed.py — reconcile_seed(conn) drops origin='seed' rows on any Sofia day fully covered by 'sync' data; idempotent; CLI --app-db.
  • Tests: tests/core/test_healthkit.py, tests/scripts/test_seed_app_db.py (synthetic baseline.db + migrated temp app.db, DST-boundary), tests/scripts/test_reconcile_seed.py.
Out of scope other epics
  • The live /sync ingest path (UUID-upsert, applying the whitelist to wire samples, daily_metrics recompute) — E5. This phase defines the whitelist E5 reuses, not /sync.
  • daily_metrics / the 7/28-day rollups / 30-day baselines — E6. The seed exists so those have data; it does not compute them.
  • Building baseline.db (export.xml → corpus) — E4·P1; deriving profile.yaml constants — E4·P2.
  • Defining/altering the app.db ingest schema — owned by E2·P2 (no model edits, no new migration); the Sofia period helpers — E2·P1 (reused).
  • Wiring into a deploy/CI step or scheduler — these are manual, one-time ops.
  • Dropped stack — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/vecs. Plain sqlite3.

Research summary

baseline.db structurally mirrors the app.db ingest tables (DB.md §1, §6; ARCH §3), so the 90-day seed is a near-straight copy modulo the three deltas above. The window is the trailing ~90 days by Europe/Sofia day boundaries — the cut is on each sample's period_date (E2·P1 app/core/time.py), never a fixed UTC offset, so a near-midnight winter/summer sample lands on the correct Sofia day (DB.md §0). The whitelist (R4) is finalized as the exact HK…Identifier set and lives in app/core/healthkit.py because it is shared with E5. The reconciliation (R5) is decided here: live 'sync' rows are authoritative, a fully-covered Sofia day drops its 'seed' rows, partial days keep theirs, 'sync' rows are never deleted. Everything is offline except the pure-data whitelist; the runtime never opens baseline.db.
Tests never read the real corpus. Tests build a tiny synthetic baseline.db + run the E2·P2 migration on a temp app.db in tmp_path — the real 1.5 GB ../db/baseline.db is never read by CI.

task 003 · reconcile

Seed↔sync reconciliation

Add scripts/reconcile_seed.py — a one-time, idempotent reconciliation (run after the first live syncs) that drops origin='seed' rows for any Europe/Sofia day fully covered by 'sync' data, keeping 'sync' rows and partially-covered seed days.

Suggested commit: feat(scripts): seed-sync reconciliation (drop seed rows on fully-synced days) · Depends on: TASK-002. Offline maintenance; plain sqlite3 + app.core.time; opens only app.db, never baseline.db. Resolves DB.md §7's open item.

The rule (this phase's decision)

Decided per day
  • A Sofia day D is "fully covered" iff ≥1 'sync' row exists whose Sofia day is D → drop all origin='seed' rows on D.
  • Scope = the origin-bearing tables records + workouts (+ their stats) only.
  • Days with no sync row keep their seed rows (partial = not covered).
  • 'sync' rows are never deleted; a second run deletes 0 (idempotent).
Rejected per type
  • Per-type coverage (drop seed only for the metrics the sync replaced) was considered.
  • It leaves a day's rollup mixing seed+sync for the same metric, defeating "sync authoritative for that day".
  • The epic frames coverage per day, not per type.
EXCLUDEDactivity_summary is not reconciled — no origin column; its date-PK upsert already collapsed seed/sync (a live /sync overwrote the day's row by date).

  • Idempotent — a second reconcile_seed(conn) run deletes 0 rows (all-zero counts).
