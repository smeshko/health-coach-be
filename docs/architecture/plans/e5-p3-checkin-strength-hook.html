The recompute seam (E6 contract)

The seam is the deliverable, not an engine. This phase defines the contract E6 implements and proves the hook fires with the exact affected-date set; E6 later overrides the provider with the real engine and needs no route change.

This phase ships seam only
  • RecomputeDailyMetrics — a typing.Protocol callable (dates: set[date]) -> None
  • noop_recompute(dates) — the default no-op; reads/writes no daily_metrics
  • affected_dates(request) -> set[date] — the canonical Sofia-date fan-out set
  • An injection point in the route (Depends(get_recompute)) defaulting to noop_recompute
E6 supplies later engine
  • The concrete RecomputeDailyMetrics implementation that reads committed rows
  • Sleep / HRV / RHR / zone-min / nutrition rollups + 30-day baselines
  • Wired in by swapping the provider only — no route edit
FAN-OUT RULEEvery touched datum buckets to its Europe/Sofia date via to_sofia(...).date() — never the wire offset — so an offset-crossing sample lands on the Sofia day (ARCHITECTURE §4).

Research summary

DB.md §3 fixes the two target tables: checkins has date as its TEXT PK ("upsertable by date") and is objective-only — gi_symptoms/illness (0/1) and knee_pain (0–10), no body-weight field (weight is the HealthKit body_mass record → daily_metrics.body_weight); strength_tests keeps a surrogate id PK with iso_week carrying a UNIQUE constraint ("one test per week"), and the server derives that iso_week from the test's date. Period keys are YYYY-Www, derived through the Europe/Sofia tz database (DST-aware), never a fixed offset — so the E2·P1 iso_week(...) helper is the single authority.
DB.md §6 is explicit that the /sync write path ends with "then recompute daily_metrics for affected dates" — but the recompute engine is E6 (epic §3/§7), so this phase defines a clean callable seam and asserts the hook is fired with the exact affected-date set. E5·P2 already shipped the /sync endpoint with checkinSaved/strengthTestSaved stubbed false; this phase flips them by returning the two services' booleans (MODELS SyncResponse).

Server-derived iso_week

The client sends only a date; the server derives the week. The E2·P1 iso_week(dt) helper takes an aware datetime and rejects naive ones, so the bare calendar date is combined to local midnight in Europe/Sofia — not a UTC combine — before the call.

# midnight-Sofia combine keeps the derived week == the calendar date's own ISO week dt = datetime.combine(test.date, time.min, tzinfo=ZoneInfo("Europe/Sofia")) week = iso_week(dt) # YYYY-Www — never read off the client (epic R4)
Why local midnight, not UTC: a UTC combine near the day boundary could shift the resulting Sofia day and thus the week. A test asserts the derived iso_week equals "%04d-W%02d" % test.date.isocalendar()[:2] for every case — pinning the day-boundary off-by-one.

affected_dates(...) fan-out

  • Each records[*].start and workouts[*].start → to_sofia(start).date() — an offset crossing the Sofia day boundary buckets to the Sofia date, not the wire offset (ARCHITECTURE §4).
  • Each activity_summary[*].date (already a calendar date) used directly.
  • checkin.date and strength_test.date when present (each a calendar date).
  • Returned as a de-duplicated set[date] — possibly empty (empty body, or only non-whitelisted records); that is fine.
Use to_sofia(...).date(), not period_date(...): the set must hold date objects, not YYYY-MM-DD strings — period_date returns a string. to_sofia is the only tz authority for the datetime→Sofia-date bucketing.

Route extension — app/api/routes/sync.py

# inside the existing single transaction, after records/workouts/activity upserts: checkin_saved = upsert_checkin(session, body.checkin) # TASK-001 strength_test_saved = upsert_strength_test(session, body.strength_test) # TASK-002 session.commit() # one transaction; rollback + re-raise on error # AFTER commit — ALWAYS, even for an empty set — via the injected provider: recompute(affected_dates(body)) # recompute: RecomputeDailyMetrics = Depends(get_recompute) return SyncResponse(..., checkin_saved=checkin_saved, strength_test_saved=strength_test_saved, ...)
  • Injection point: a provider def get_recompute() -> RecomputeDailyMetrics: return noop_recompute, injected via recompute: RecomputeDailyMetrics = Depends(get_recompute) — a test app.dependency_overrides a spy; E6 overrides the provider with the real engine, no route edit.
  • Unconditional call: even an empty affected set is passed through (noop_recompute(set()) and a real engine both handle set() harmlessly) — deterministic, not a skip-vs-call guess.
  • Post-commit firing: the future E6 engine reads committed rows; a recompute error can't roll back a good ingest.
  • Completes the stubs: returns the real checkin_saved/strength_test_saved (replacing E5·P2's False); records/workouts/activity counts and server_time=now_sofia() unchanged; still no readiness computation.
