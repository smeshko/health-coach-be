Stand up the runtime-database engine, WAL, declarative base, Europe/Sofia period-key helpers and Alembic — all targeting app.db only — so E2·P2/P3 can attach the nine tables. This phase ships no tables.

Goal

Engine + WAL + base + Sofia time + Alembic, app.db only. Build the runtime engine, the WAL/FK connect listener, the declarative Base with naming conventions, the Europe/Sofia period-key/timestamp helpers, and Alembic — every piece pointed at app.db — so the nine tables can attach in E2·P2/P3. The initial migration is empty: this phase creates zero tables of its own.

Scope vs out-of-scope

In scope this phase
  • app/database/engine.py — make_engine(db_path), lazy cached get_engine(), SessionLocal, get_session(), side-effect-free set_sqlite_pragmas connect listener.
  • app/database/base.py — declarative Base over a MetaData carrying a naming_convention (ix/uq/ck/fk/pk).
  • app/core/time.py — period_date → YYYY-MM-DD, iso_week → YYYY-Www, plus offset-preserving timestamp helpers.
  • Alembic — alembic.ini + env.py + script.py.mako + an empty initial migration targeting app.db only.
  • Deps — add alembic and tzdata to pyproject.toml.
Out of scope later phases
  • The nine tables — records/workouts/workout_statistics/activity_summary (E2·P2); daily_metrics/checkins/strength_tests/plans/suggestions (E2·P3). Zero tables here.
  • The R5 UNIQUE/index/FK constraints themselves — only their names are guaranteed deterministic now.
  • Writing data (E5 /sync), computing daily_metrics (E6), profile.yaml (E3), seeding from baseline.db (E4) — baseline.db is never opened here.
  • Dropped stack — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/vecs.

Why app.db only — the two-DB lifecycle

app.db is the only database the running API touches; baseline.db is a read-only build input, regenerated by build_db.py (DROP TABLE …) and never opened at runtime — so Alembic and the engine must target app.db exclusively (DB.md §0; ARCHITECTURE §3).

Load-bearing split: pointing Alembic at the build input would let a migration drop or mutate the read-only corpus. env.py never names baseline.db; a grep guard proves the string appears nowhere.

Timestamps & period keys

  • WAL must actually be on — backup is litestream streaming the WAL to object storage, so WAL is set via a SQLAlchemy connect event listener issuing PRAGMA journal_mode=WAL on every new DBAPI connection (ARCHITECTURE §1; epic R1).
  • Timestamps stored as ISO-8601 TEXT carrying the per-sample offset HealthKit emits — Europe/Sofia is +02:00/EET winter, +03:00/EEST summer, plus travel; never hard-coded. They sort correctly and stay debuggable as TEXT (DB.md §0; ARCHITECTURE §4; epic R2).
  • Period keys derived through the Europe/Sofia tz database via zoneinfo, DST-aware — date and iso_week → YYYY-Www (e.g. 2026-W23), the cache key for plans and period derivation for later epics.
  • A naming_convention on the declarative MetaData makes E2·P2/P3 autogen diffs deterministic for the R5 constraints.

Key decisions

decisionrationale
Period-key helpers in app/core/time.py, not app/database/time.pyPeriod keys are a domain/time concern used by many epics (E5/E6/E10/E11), not a DB-engine concern — keeps the DB layer out of week-key formatting.
WAL set via a connect event listener, not a one-off at startupEvery pooled connection — and every fresh temp DB in tests — is in WAL. The same listener issues PRAGMA foreign_keys=ON (SQLite defaults it OFF per connection; E2·P2 adds a FK). set_sqlite_pragmas is side-effect-free so env.py reuses it (round-1 #1).
Runtime engine is lazy (get_engine()), not built at importA module-level engine would resolve app_db_path the moment any module (incl. Alembic env.py) loads and could bind the wrong DB before a test override applies (round-1 #1, #4).
Alembic URL owned by settings; static sqlalchemy.url ignoredresolve_url() returns sqlite:///{settings.app_db_path} in production, ignores any .ini sqlalchemy.url, and accepts only the explicit config.attributes["test_db_url"] override (round-1 #2).
The initial migration is emptyNo tables this phase. An empty revision still exercises the upgrade/downgrade round-trip and proves the wiring + Base.metadata target + naming convention are sound.
Add tzdata as a dependencyZoneInfo("Europe/Sofia") needs the IANA tz database; some containers/CI lack the system copy, so the portable PyPI fallback guarantees DST-aware period keys everywhere.
Timestamps stored as raw ISO-8601 TEXT, offset preserved verbatimNever normalized to UTC or a fixed +03:00. store_ts(s) validates and returns the exact string; helpers parse the offset present, they do not impose one.
Period-key helpers reject naive datetimes (no host-tz fallback)astimezone() on a naive value silently uses the host local timezone → machine-dependent cache keys. Aware-only is enforced (round-2 #3).

task-003 · app.core.time

Europe/Sofia period-key & timestamp helpers

Add DST-aware Europe/Sofia period-key helpers — period_date → YYYY-MM-DD, iso_week → YYYY-Www — and timestamp helpers that parse and preserve the per-sample offset HealthKit emits, never hard-coding +03:00.

Goal: Sofia-local period keys + verbatim offset-preserving timestamp helpers, in core (not the DB layer). Depends on: none. Commit: feat(core): add Europe/Sofia period-key and timestamp helpers.

Files

pathchangedetail
app/core/time.pynewthe helper module (see signatures below).
tests/core/__init__.pynewpackage marker (ensure present).
tests/core/test_time.pynewDST-boundary, travel-offset, ISO-year-boundary, and offset-preservation cases.

Helper surface

helperbehaviour
SOFIA = ZoneInfo("Europe/Sofia")the DST-aware tz the period keys resolve through.
parse_ts(value: str) → datetimedatetime.fromisoformat preserving tzinfo/offset; raises on a naive/offset-less string. Used for derivation only.
store_ts(value: str) → strthe storage helper — validates the input is offset-aware ISO-8601 and returns the original string unchanged (no offset reformatting, no fractional-second normalization, no UTC rewrite) (round-1 #3).
_require_aware(dt) → Noneraises ValueError if dt.tzinfo is None or dt.utcoffset() is None (round-2 #3).
to_sofia(dt) → datetime_require_aware(dt) then dt.astimezone(SOFIA).
period_date(dt) → strSofia-local calendar date as YYYY-MM-DD (via to_sofia).
iso_week(dt) → strSofia-local ISO week as zero-padded YYYY-Www — "%04d-W%02d" from to_sofia(dt).isocalendar().
period_date_of(ts) / iso_week_of(ts)string convenience wrappers that parse_ts first.

Acceptance

  • DST-aware conversion — a UTC instant near the late-March EET→EEST and a late-October EEST→EET transition map to the correct Sofia-local date/week (not the UTC date).
  • Travel offset — a non-Sofia offset (e.g. 2026-06-15T23:30:00+09:00) yields the correct Sofia-local date/iso_week, proving conversion through the tz db (not the literal offset).
  • ISO-week formatting — zero-padded YYYY-Www (e.g. 2026-W23), correct at an ISO year boundary (a week belonging to the adjacent ISO year).
  • Verbatim storage — store_ts(s) == s for +02:00, +03:00, compact +0300, a non-Sofia offset, and a fractional-seconds case; parse_ts(s).utcoffset() equals the input offset.
  • Naive rejected — parse_ts/store_ts on a naive string raise; to_sofia/period_date/iso_week raise ValueError on a naive datetime (no host-tz fallback) (round-2 #3).
  • tz data — ZoneInfo("Europe/Sofia") resolves (tzdata present).
