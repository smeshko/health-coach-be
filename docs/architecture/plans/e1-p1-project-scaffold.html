Project scaffold & config

Stand up the runnable uv/FastAPI chassis — package layout, typed env settings, and the camelCase Pydantic base — so every later epic has something to build on.

Goal

Deliver the chassis: a uv-managed, Python 3.13 FastAPI skeleton with a package layout, typed env Settings, and a shared camelCase Pydantic base — nothing more. This phase produces the structure every later epic imports.

Epic context

  • Epic E1 — Foundation & API Skeleton, phase P1. Source of truth: epics/E01-foundation.md.
  • Grounded in ARCHITECTURE.md §1 (stack note) and MODELS.md "Conventions" (casing, nulls vs absent).
  • Status: draft · Risk: small · 4 implementation tasks + 1 final-validation task.

Scope vs Out-of-Scope

In scope this phase
  • uv project pinned to Python 3.13 (requires-python = ">=3.13,<3.14"), kept-stack deps only.
  • Package layout: app/ with api/, core/, database/, services/ + tests/.
  • FastAPI app factory create_app() + a uvicorn entrypoint.
  • Typed settings (pydantic-settings) read from env; fail fast on missing required vars.
  • A camelCase Pydantic base (alias_generator=to_camel, populate_by_name=True).
Out of scope later phases
  • Auth, error envelope, health endpoint → E1·P2.
  • Workflow engine primitives → E1·P3.
  • DB models / migrations → E2.
  • Real endpoints → E5 / E10 / E11.
  • Docker / Langfuse wiring → E12.
STACK ALLOWLISTNo Postgres / Celery / Redis / pgvector / vecs / Supabase deps anywhere (ARCHITECTURE §1).

Research summary

Where the chassis comes from, and what it deliberately drops.

  • Reuse Datalumina's GenAI Launchpad (../genai-launchpad-main) — keep only its FastAPI app, core/ workflow primitives, PydanticAI, Jinja2, and Alembic.
  • Drop Postgres/pgvector, Celery, Redis, Supabase, streaming and RAG (ARCHITECTURE §1). Single synchronous process — no workers/scheduler.
  • Wire JSON is camelCase, Python stays snake_case behind a Pydantic alias_generator (MODELS "Conventions").
  • The Launchpad layout under ../genai-launchpad-main/app/ is the reference for the package structure to mirror (minus the dropped pieces).

Acceptance criteria

The phase's contract — every box must be green before E1·P1 is done. Final validation (page 06) maps concrete checks back to each of these.

  • uv sync installs the project on Python 3.13 (requires-python bounded >=3.13,<3.14); the locked dependency set contains none of Postgres/Celery/Redis/pgvector/vecs.
  • uvicorn starts the app via the factory entrypoint without error when env is complete.
  • Settings load from env and fail fast at app startup (create_app() raises) when a required var is missing — proven by a negative app-factory smoke, not only an isolated settings test.
  • A sample model inheriting the base emits camelCase from raw model_dump_json() and over the wire (FastAPI route), and accepts both snake_case and camelCase input.
  • The package layout (api/, core/, database/, services/, tests/) exists and is importable.

A shared Pydantic base that serializes camelCase on the wire while keeping snake_case in Python, inherited by every request/response model.

Goal: one CamelModel base that every E5/E10/E11 wire model inherits — casing defined once. Commit: feat(api): add camelCase Pydantic base model

Files

pathchangenote

Acceptance

  • A model with snake_case fields inheriting CamelModel emits camelCase keys from raw model_dump_json() (no by_alias=True needed at the call site) — aliasing is configured on the model, not left to the caller.
  • A FastAPI route returning the model produces camelCase JSON on the wire (asserted via TestClient).
  • It accepts both camelCase (alias) and snake_case (field name) on input.
  • Null-vs-absent (MODELS "Nulls vs absent"): an optional field declared T | None = None accepts both omission and explicit null (tested) — the convention T | None = None is documented in the module docstring so later wire models don't reject omission.
