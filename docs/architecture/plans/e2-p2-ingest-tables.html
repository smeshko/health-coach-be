Ingest tables — schema only

Define the four HealthKit ingest tables as SQLAlchemy models plus one Alembic migration that creates them on app.db with their exact UNIQUE / index / FK constraints. Schema only — this phase never writes data.

Goal

Goal: Define the four ingest SQLAlchemy models (records, workouts, workout_statistics, activity_summary) under app/database/models/ and an Alembic migration that creates them on app.db with the exact UNIQUE / index / FK constraints from DB.md §1 — schema only, no data.

Epic & dependency context

Epic E2 — Persistence Layer (app.db), phase P2. The four ingest tables mirror baseline.db so the 90-day seed (E4) is a near-straight copy — with exactly two additions per row: a unique uuid (the /sync idempotency key) and an origin flag.

Scope vs. out of scope

In scope this phase
  • models/records.py — Records mirroring baseline.db + uuid / origin; UNIQUE(uuid), index (type, start_date), index (start_date).
  • models/workouts.py — Workouts; UNIQUE(uuid); adds effort_score (RPE) + physical_effort (METs), absent from baseline.
  • models/workout_statistics.py — WorkoutStatistics; workout_id FK → workouts(id); index (workout_id, type).
  • models/activity_summary.py — ActivitySummary; TEXT date PK (explicit NOT NULL).
  • models/__init__.py — re-export all four so Base.metadata sees them for autogenerate.
  • One Alembic migration — down_revision = E2·P1 initial; creates four tables; downgrade() drops in FK-safe order.
  • Tests (tests/database/) — round-trip, column/type/constraint introspection.
Out of scope later phases
  • Writing / upserting — ON CONFLICT(uuid) DO NOTHING, the date-upsert, type-whitelist, daily_metrics recompute → E5 (/sync).
  • Seeding from baseline.db + the date_components→date rename → E4 (trailing ~90 days, origin='seed').
  • The other five tables — daily_metrics, checkins, strength_tests, plans, suggestions → E2·P3.
  • Engine / WAL / Alembic scaffolding / helpers — delivered in E2·P1; reused here.
  • Finalizing the HealthKit type-whitelist — resolved before the first sync (E5), not a schema constraint here.
  • Dropped stack — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/vecs.

Research summary

  • Mirror + two additions — the four ingest tables structurally mirror baseline.db so the 90-day seed is a near-straight copy; the only additions are a unique uuid (idempotency key) and an origin flag ('seed' from baseline | 'sync' live).
  • uuid UNIQUE but nullable — seeded rows carry no HealthKit UUID (NULL); SQLite/ANSI treat multiple NULLs as distinct, so the unique index admits every seeded row while still rejecting duplicate live UUIDs.
  • Exact uniqueness/indexing (epic R5) — records → UNIQUE(uuid) + (type, start_date) + (start_date); workouts → UNIQUE(uuid); workout_statistics → index (workout_id, type) + FK to workouts(id); activity_summary → date is the PK (upsert key).
  • Timestamps are ISO-8601 TEXT — offset preserved as emitted (E2·P1 helpers); period keys go through Europe/Sofia (E2·P1).
  • Purpose-built workout columns — effort_score (RPE 1–10) and physical_effort (METs) do not exist in baseline.db (ARCHITECTURE §3).
  • FK drop order — downgrade() must drop workout_statistics before workouts; E2·P1's connect listener already enables PRAGMA foreign_keys=ON so the FK is enforced at runtime.

Decisions

decisionrationale
One module per table under models/, re-exported from __init__.pyKeeps each table reviewable in isolation; gives Alembic a single import (import app.database.models) registering all four on the shared Base.metadata.
records.uuid & workouts.uuid are UNIQUE + nullableSeeded rows carry NULL uuid; SQLite treats each NULL as distinct under a UNIQUE index, so all seed rows coexist while a duplicate non-NULL uuid is rejected — exactly the idempotency contract.
activity_summary.date is the PK (no surrogate id), declared explicit NOT NULLThe natural upsert/cache key (one Apple-rings row per Europe/Sofia day). A non-WITHOUT ROWID TEXT PK is NULL-tolerant in SQLite, so the column is forced primary_key=True, nullable=False.
All timestamp columns are TEXT, never DATETIMEThe contract stores ISO-8601 TEXT carrying HealthKit's per-sample offset; a DateTime type would invite normalization. String / Text keeps the offset verbatim and still sorts correctly.
workout_id FK via ForeignKey("workouts.id"); downgrade drops children firstThe FK is enforced (E2·P1's foreign_keys=ON), so downgrade() drops workout_statistics before workouts to avoid a drop-order error on round-trip.
Constraint / index names come from E2·P1's naming_conventionModels declare UniqueConstraint / Index and let metadata's convention (uq / ix / fk / pk) name them — deterministic autogenerate, assertable names.
One migration for all four tables (not four)They form one cohesive ingest unit landing in a single PR; one revision keeps the down_revision chain simple and the up/down round-trip atomic.
No data, no write path in this phaseTests assert constraints by attempting raw duplicate inserts (a constraint check, not the /sync upsert); the idempotent write path is E5.

Acceptance criteria

The phase's contract — every item is a concrete, introspectable check on the migrated DB or the model layer. All must hold before the phase is done.

Schema & round-trip

  • Four ingest tables created — after alembic upgrade head on a temp file DB, sqlite_master contains records, workouts, workout_statistics, activity_summary (plus alembic_version). (epic §3, §4; DB.md §1)
  • Round-trip — upgrade head → downgrade base → upgrade head succeeds on a temp file DB; after downgrade base none of the four ingest tables exist; the FK drop order (workout_statistics before workouts) does not error. (epic §4, §6)
  • Models registered on metadata — set(Base.metadata.tables) includes all four after import app.database.models. (epic E2·P2)
  • No baseline / dropped-stack leakage — grep -rn baseline alembic finds nothing new; grep -REn "psycopg|pgvector|celery|redis|supabase|vecs" app is empty. (DB.md §0; ARCHITECTURE §1)
  • Lint + suite — uv run ruff check . and uv run pytest tests/database pass.

records columns, indexes & uuid

  • Columns & types — PRAGMA table_info(records): id INTEGER PK; uuid TEXT (nullable); type TEXT NOT NULL; unit TEXT; value REAL; value_text TEXT; source_name/source_version/device TEXT; creation_date TEXT; start_date TEXT NOT NULL; end_date TEXT; origin TEXT NOT NULL.
  • Indexes — a UNIQUE index on (uuid), a non-unique index on (type, start_date), a non-unique index on (start_date).
  • uuid UNIQUE, NULL-tolerant — inserting two rows with uuid=NULL both succeed; inserting two rows with the same non-NULL uuid raises IntegrityError.

workouts & workout_statistics

  • workouts columns & types — id INTEGER PK; uuid TEXT (nullable, UNIQUE); activity_type TEXT NOT NULL; duration/total_distance/total_energy_burned REAL with their *_unit TEXT; effort_score REAL nullable; physical_effort REAL nullable; provenance + creation_date TEXT; start_date TEXT NOT NULL; end_date TEXT; origin TEXT NOT NULL.
  • workouts.uuid UNIQUE, NULL-tolerant — two uuid=NULL rows both succeed (the E4 seed path); two rows with the same non-NULL uuid raise IntegrityError. (round-1 #2)
  • workout_statistics FK + index — PRAGMA foreign_key_list shows workout_id → workouts(id); an index on (workout_id, type) exists; inserting a row whose workout_id does not exist raises IntegrityError.
  • workout_statistics columns — id PK, workout_id INTEGER NOT NULL, type TEXT NOT NULL, start_date/end_date TEXT, sum/average/minimum/maximum REAL, unit TEXT.

activity_summary PK & types

  • date is the PK and NOT NULL — PRAGMA table_info reports pk=1 and notnull=1 for date; inserting a row with date=NULL raises IntegrityError. (round-1 #1)
  • Affinities — active_energy_burned(+_goal), apple_exercise_time(+_goal), apple_move_time(+_goal) are REAL; apple_stand_hours(+_goal) are INTEGER.
