## Goal

Define the five remaining SQLAlchemy models — one derived (`daily_metrics`) and four coaching-state
(`checkins`, `strength_tests`, `plans`, `suggestions`) — under `app/database/models/` plus an Alembic
migration that creates them with the exact `UNIQUE`/PK constraints from DB.md §2–§4, completing the
**9-table** `app.db` with **no `profile` table** — schema only, no data.

## Scope

- **`app/database/models/daily_metrics.py`** — `DailyMetrics` model mapped to `daily_metrics`, one row per
  Europe/Sofia day (DB.md §2): `date` `Text` **`primary_key=True, nullable=False`** (the per-day key — no
  surrogate `id`; explicit `nullable=False` because a SQLite non-`WITHOUT ROWID` TEXT PK is NULL-tolerant);
  `sleep_h` / `hrv_sdnn` / `rhr` / `hrv_30d_mean` / `hrv_30d_sd` / `rhr_30d_mean` `Float`; `steps`
  `Integer`; `active_energy` `Float`; `z1_min` / `z2_min` / `z3_min` / `z4_min` / `z5_min` `Float`;
  nutrition intake `kcal_in` / `protein_in_g` / `carbs_in_g` / `fat_in_g` / `fiber_in_g` / `sodium_in_mg` /
  `water_in_l` `Float`; `body_weight` `Float`; `hard_day` `Integer` (0/1); `readiness_score` `Integer`
  **nullable** (filled later by the daily brief, E11); `band` `Text` **nullable** (`GREEN`/`AMBER`/`RED`);
  `computed_at` `Text`.
- **`app/database/models/checkins.py`** — `Checkins` model mapped to `checkins` (DB.md §3): `date` `Text`
  **`primary_key=True, nullable=False`** (upsertable by date); `gi_symptoms` `Integer` (0/1); `illness`
  `Integer` (0/1); `knee_pain` `Integer` (0–10, 0 = none); `created_at` / `updated_at` `Text`. Objective-only
  — **no body-weight field** (weight is HealthKit `body_mass` → `daily_metrics.body_weight`).
- **`app/database/models/strength_tests.py`** — `StrengthTests` model mapped to `strength_tests` (DB.md §3):
  `id` `Integer` PK; `date` `Text` `nullable=False`; `iso_week` `Text` `nullable=False` with a
  `UniqueConstraint("iso_week")` (one test per week); `max_pushups` / `max_pullups` `Integer`; `created_at`
  `Text`.
- **`app/database/models/plans.py`** — `Plans` model mapped to `plans` (DB.md §4): `id` `Integer` PK;
  `iso_week` `Text` `nullable=False` with a `UniqueConstraint("iso_week")` (one plan per ISO week →
  cache key); `payload` `Text` `nullable=False` (JSON-as-TEXT); `rationale` `Text`; `inputs_snapshot` `Text`
  (JSON-as-TEXT); `model` `Text`; `constitution_version` `Text`; `created_at` `Text`.
- **`app/database/models/suggestions.py`** — `Suggestions` model mapped to `suggestions` (DB.md §4): `id`
  `Integer` PK; `date` `Text` `nullable=False` with a `UniqueConstraint("date")` (one suggestion per day →
  cache key); `readiness_score` `Integer`; `band` `Text`; `safety_gate_tripped` `Integer` (0/1);
  `gate_reason` `Text` **nullable**; `payload` `Text` `nullable=False` (JSON-as-TEXT); `inputs_snapshot`
  `Text` (JSON-as-TEXT); `model` / `constitution_version` / `created_at` `Text`.
- **`app/database/models/__init__.py`** — extend E2·P2's re-exports to import all five new models so
  `import app.database.models` registers them on the shared `Base.metadata` for Alembic autogenerate.
- **One Alembic migration** under `alembic/versions/` (autogenerated then hand-checked), **authored complete
  in TASK-003 in a single revision** — `down_revision` = E2·P2's `ingest_tables` head revision; `upgrade()`
  creates **all five** tables with the exact PK/UNIQUE constraints; `downgrade()` drops them (none have
  inter-table FKs, so drop order is free). TASK-001/002 add only models (validated via `create_all`), so no
  intermediate/partial revision is ever stamped.
- **Tests** (`tests/database/`) — Alembic `upgrade head`→`downgrade base`→`upgrade head` round-trips with
  all five tables; after `upgrade head` the DB holds **exactly the 9 tables** (records, workouts,
  workout_statistics, activity_summary, daily_metrics, checkins, strength_tests, plans, suggestions) plus
  `alembic_version` and **no `profile` table**; `UNIQUE(iso_week)` on `plans` and `strength_tests` and
  `UNIQUE(date)` on `suggestions` reject duplicates; `daily_metrics.date` / `checkins.date` are NOT-NULL
  PKs; `daily_metrics.readiness_score` and `daily_metrics.band` accept NULL; column types/affinities match
  DB.md §2–§4.

## Out of Scope

- **Writing / upserting data** — `checkins` date-upsert, `strength_tests` weekly write, computing any
  `daily_metrics` value (sleep/HRV/zone-min/nutrition rollups), filling `readiness_score`/`band`, and the
  get-or-generate brief cache writes for `plans`/`suggestions` are E5 (`/sync`), E6 (derived metrics),
  E10 (weekly brief), E11 (daily brief). This phase defines **only schema + migration** and asserts
  constraints; it never exercises a write path (epic §3 note, §7; DB.md §6).
- **`profile.yaml`** — the constants file (athlete profile, zones, nutrition) is E3 and is explicitly
  **NOT a DB table** (DB.md §0, §5; epic R3); this phase must leave the 9-table set without a `profile`
  table.
- **The `?refresh=true` delete-and-regenerate flow** and readiness/safety-gate computation that populate
  `suggestions.safety_gate_tripped`/`gate_reason` and snapshot `readiness_score`/`band` back onto
  `daily_metrics` — E11/E8 (DB.md §4, §6; ARCHITECTURE §4).
- **The four ingest tables** (`records`, `workouts`, `workout_statistics`, `activity_summary`) — delivered
  in E2·P2; this phase only adds the derived + coaching-state tables and chains its migration off the
  ingest revision.
- **Engine / WAL / Alembic scaffolding / period-key & timestamp helpers** — delivered in E2·P1; this phase
  reuses `get_engine`/`set_sqlite_pragmas`/`Base`/`metadata` and the configured `alembic/` without
  re-creating them. The DST period-key helper tests live in E2·P1 (epic §6); they are not re-asserted here.
- **Dropped stack** — Postgres/pgvector, Celery, Redis, Supabase, streaming, RAG/`vecs`
  (ARCHITECTURE §1 stack note).

## Research Summary

This phase adds the **five** non-ingest tables that complete `app.db`'s **9-table** set (DB.md §0; epic
R3): one **derived** materialized cache (`daily_metrics`, one row per Europe/Sofia day — DB.md §2) and four
**coaching-state** tables (`checkins`/`strength_tests` inputs, `plans`/`suggestions` brief-cache outputs —
DB.md §3–§4). The load-bearing constraints are the cache keys: **`UNIQUE(iso_week)`** on `plans` and
`strength_tests`, and **`UNIQUE(date)`** on `suggestions` — the "one brief / one test per period"
guarantee the get-or-generate flow relies on (DB.md §4; ARCHITECTURE §4). `daily_metrics` and `checkins`
use the natural `date` as a TEXT **PK** (per-day / upsert-by-date), while `strength_tests`/`plans`/
`suggestions` keep a surrogate `id` PK with the period column carrying the UNIQUE constraint instead
(DB.md §2–§4). Two fields are explicitly **nullable** and must round-trip NULL: `daily_metrics.readiness_score`
and `band` are filled later by the daily brief (DB.md §2 "nullable until the daily brief runs"), and
`suggestions.gate_reason` is NULL unless the safety gate trips (DB.md §4). `payload` is `NOT NULL` on both
`plans` and `suggestions`; `inputs_snapshot`/`rationale` are nullable JSON/text snapshots (DB.md §4). All
timestamps (`computed_at`, `created_at`, `updated_at`) and JSON columns are stored as **TEXT** to preserve
the emitted offset and avoid normalization (DB.md §0; E2·P1, epic R2). There is deliberately **no `profile`
table** — those constants live in `profile.yaml` (E3); a positive test asserts the table set is exactly the
9 expected and `profile` is absent (DB.md §0, §5; epic R3). The check-in is objective-only with **no
body-weight field** (weight comes from HealthKit `body_mass`; DB.md §3, ARCHITECTURE §3). None of the five
tables has an inter-table FK, so the migration `downgrade()` drop order is unconstrained; E2·P1's connect
listener (`PRAGMA foreign_keys=ON`, WAL) and `naming_convention` (`uq`/`pk`/`ix`) still apply so the
autogenerated migration is deterministic and the constraint names are assertable.

## Decisions

- **Models live in `app/database/models/` as one module per table, re-exported from `models/__init__.py`** —
  continues the E2·P2 pattern: each table reviewable in isolation, one import (`import app.database.models`)
  registers all nine on the shared `Base.metadata` for autogenerate (epic E2·P3; mirrors E2·P2).
- **`daily_metrics.date` and `checkins.date` are TEXT PKs (no surrogate `id`), declared
  `primary_key=True, nullable=False`** — DB.md §2/§3 make `date` the PK (one row per Europe/Sofia day /
  upsert-by-date), matching the `activity_summary` date-PK pattern from E2·P2. SQLite's non-`WITHOUT ROWID`
  TEXT PK is NULL-tolerant, so the explicit `nullable=False` is required to stop multiple `date=NULL` rows
  silently breaking the per-day uniqueness (E2·P2 round-1 #1; DB.md §2–§3).
- **`strength_tests`/`plans`/`suggestions` keep a surrogate `id` PK and put the period uniqueness on a
  separate UNIQUE column** — DB.md §3/§4 specify `id` PK + `iso_week` UNIQUE (strength_tests/plans) and
  `id` PK + `date` UNIQUE (suggestions). The surrogate `id` is the row identity; the period column is the
  cache key the get-or-generate flow looks up and the UNIQUE constraint enforces "one per period"
  (DB.md §4; ARCHITECTURE §4; epic R5).
- **`readiness_score`/`band` on `daily_metrics` and `gate_reason` on `suggestions` are `nullable=True`** —
  DB.md §2 says `readiness_score` is "nullable until the daily brief runs" and `band` is filled alongside
  it; DB.md §4 marks `gate_reason` nullable (only set when the gate trips). A row created at sync time (E5)
  before any brief must persist with these NULL, so the columns must accept NULL and a test inserts a row
  leaving them unset and reads NULL back (DB.md §2, §4).
- **`payload` is `NOT NULL` on `plans` and `suggestions`; `inputs_snapshot`/`rationale` nullable** — DB.md §4
  marks `payload` `TEXT NOT NULL` (a cached brief without its payload is meaningless), while
  `inputs_snapshot`/`rationale` are reproducibility/explanation snapshots that may be absent. The model
  declares `payload nullable=False` and the others `nullable=True` (DB.md §4).
- **JSON columns (`payload`, `inputs_snapshot`) are stored as `Text`, not a JSON type** — SQLite has no
  native JSON storage type (JSON1 operates on TEXT), and the contract is JSON-as-TEXT (DB.md §4). Using
  `Text` keeps the migration portable and the stored bytes verbatim; serialization/validation is the
  brief-generation layer's job (E10/E11), out of scope here.
- **All timestamp columns are `Text`, not SQLite `DATETIME`** — the contract (E2·P1, epic R2, DB.md §0)
  stores ISO-8601 TEXT carrying the per-sample offset; `computed_at`/`created_at`/`updated_at` follow the
  same rule so nothing normalizes the offset away (DB.md §0).
- **`hard_day`, `gi_symptoms`, `illness`, `safety_gate_tripped` are `Integer` (0/1); `knee_pain` is
  `Integer` (0–10)** — DB.md §2–§4 store these as INTEGER flags/scores (SQLite has no native boolean). The
  0/1 and 0–10 ranges are application invariants enforced at the write layer (E5/E11), not DB CHECK
  constraints, so the schema stays a faithful mirror of DB.md without inventing constraints the docs don't
  specify (DB.md §2–§4; epic §7).
- **One migration for all five tables, authored complete in TASK-003 (not five revisions, and not grown
  task-by-task)** — they land in one cohesive phase/PR; a single revision (`down_revision` = the E2·P2
  `ingest_tables` head) keeps the chain linear and the up/down round-trip atomic (epic §3 E2·P3, §4).
  Crucially, **TASK-001/002 deliver only the SQLAlchemy models** (validated via engine-level
  `Base.metadata.create_all` on temp DBs) and **add no Alembic revision**; the single `state_tables`
  revision creating all five tables is created **once, in TASK-003**. This removes the version-skew hazard
  of a partial revision (an early-stamped revision id holding only some tables would be treated as current
  on a real DB and never create the rest — Codex round-2 #1): there is never an intermediate revision to
  stamp. The final-validation guard is still a **migration↔metadata parity check**: after `upgrade head`,
  `alembic.autogenerate.compare_metadata` against the live `Base.metadata` must emit an **empty** diff — so
  no table the models declare can be missing from the migration (Codex round-1 #1).
- **No `profile` table; a positive 9-table assertion guards it** — DB.md §0/§5 and epic R3 are explicit
  that constants live in `profile.yaml`, not the DB. A test asserts the user-table set after `upgrade head`
  is **exactly** the 9 named tables and that `profile` is absent, so a stray model can't silently add a 10th
  table or reintroduce `profile` (DB.md §0, §5; epic R3, §4).
- **No data, no write path, in this phase** — tests prove the UNIQUE/PK constraints by attempting raw
  duplicate / NULL inserts (a constraint check, not the `/sync` or get-or-generate write path); the upsert
  and brief-cache writes are E5/E10/E11 (DB.md §6; epic §7).

## Risks

- **A `UNIQUE(iso_week)` / `UNIQUE(date)` cache key is dropped or mis-named in autogenerate** → two plans /
  suggestions for the same period can coexist, silently breaking get-or-generate — mitigation: tests
  introspect the migrated DB (`PRAGMA index_list`/`index_info`, `sqlite_master`) and assert `plans` and
  `strength_tests` each have a UNIQUE index on `(iso_week)` and `suggestions` has a UNIQUE index on `(date)`;
  duplicate-insert tests over a `get_engine()` connection assert `IntegrityError` for each (DB.md §4; epic R5).
- **`readiness_score`/`band`/`gate_reason` made `NOT NULL` by mistake** → a sync-time row (no brief yet)
  can't be inserted — mitigation: the model declares them `nullable=True`; a test inserts a `daily_metrics`
  row leaving `readiness_score`/`band` unset (and a `suggestions` row leaving `gate_reason` unset) and reads
  NULL back (DB.md §2, §4).
- **A `date` TEXT PK left NULL-tolerant** (`daily_metrics`/`checkins`) → multiple `date=NULL` rows break
  per-day uniqueness — mitigation: declare `primary_key=True, nullable=False`; a test asserts `PRAGMA
  table_info` reports `pk=1` and `notnull=1` for `date` and that a `date=NULL` insert raises `IntegrityError`
  (E2·P2 round-1 #1; DB.md §2–§3).
- **`payload` accidentally nullable** → a cached brief with no body — mitigation: declare `payload
  nullable=False`; a test asserts `notnull=1` for `payload` on both `plans` and `suggestions` and that a
  NULL-`payload` insert raises `IntegrityError` (DB.md §4).
- **A stray / extra table or a reintroduced `profile` table** → epic R3 (9 tables, no `profile`) violated —
  mitigation: a test asserts the user-table set after `upgrade head` is **exactly** the 9 named tables and
  `'profile' not in` it (DB.md §0, §5; epic R3, §4).
- **Wrong column type** (e.g. `steps`/`hard_day`/`readiness_score` stored REAL not INTEGER, or a timestamp/
  JSON as a non-TEXT type) — mitigation: a test reads `PRAGMA table_info` per table and asserts the declared
  SQLite type affinity (INTEGER for `steps`/`hard_day`/`readiness_score`/`gi_symptoms`/`illness`/`knee_pain`/
  `safety_gate_tripped`/`max_pushups`/`max_pullups`/`id`s, REAL for the `daily_metrics` measurements, TEXT
  for timestamps / JSON / `band` / `iso_week` / `gate_reason`) (DB.md §2–§4; epic §4).
- **Round-trip fails on the migration chain** — mitigation: the Alembic `upgrade head`→`downgrade base`→
  `upgrade head` test proves the round-trip and that after `downgrade base` none of the five new tables (nor
  the ingest tables) remain; `down_revision` points at the E2·P2 ingest head so the chain stays linear
  (epic §4, §6).
- **Models not registered on `Base.metadata`** → autogenerate emits an empty migration — mitigation:
  `models/__init__.py` imports all five; a test asserts `set(Base.metadata.tables) ⊇ {daily_metrics,
  checkins, strength_tests, plans, suggestions}` (epic E2·P3).
- **A partial / stale `state_tables` revision** (an early-stamped revision id holding only some tables would
  be treated as current on a durable DB and never create the rest) → real DBs missing tables while fresh-DB
  tests still pass — mitigation: **no Alembic revision is created until TASK-003**; TASK-001/002 add only
  models (validated via `create_all`), so the single `state_tables` revision is authored complete (all five
  tables) in one shot and there is never an intermediate revision to stamp. Final validation also runs a
  **migration↔metadata parity** check — after `upgrade head`, `compare_metadata` against the live
  `Base.metadata` must emit an **empty** diff (no model table missing from the migration); the 9-table
  exact-set assertion is the second backstop (Codex round-1 #1, round-2 #1; DB.md §0, §2–§4).
- **Migration accidentally targets `baseline.db` / leaks a dropped-stack dep** — mitigation: reuse E2·P1's
  `alembic/env.py` (settings-owned URL, no `baseline` reference); `! grep -rn baseline alembic` and
  `! grep -REn "psycopg|pgvector|celery|redis|supabase|vecs" app` stay empty (DB.md §0; ARCHITECTURE §1).
