# TASK-004: Alembic init targeting app.db only

Depends on: TASK-001, TASK-002
Suggested commit: `feat(database): scaffold Alembic targeting app.db with empty initial migration`

## Goal

Initialize Alembic against **`app.db` only** (URL from `settings.app_db_path`, never `baseline.db`), with
`Base.metadata` as the autogenerate target and an empty initial migration that round-trips cleanly.

## Files

- `alembic.ini` — new: minimal config; `script_location = alembic`; **no** static `sqlalchemy.url` at all
  (not even a placeholder) — the URL is owned by `env.py` from settings, so a stale `.ini` cannot redirect
  a migration (round-1 #2).
- `alembic/env.py` — new:
  - import `from app.core.settings import get_settings`, `from app.database.base import Base`,
    `from app.database.engine import set_sqlite_pragmas`.
  - `target_metadata = Base.metadata` (autogenerate target).
  - **URL resolution (settings owns production):** `resolve_url()` returns the **test-only** override when
    present via a single explicit channel — `config.attributes["test_db_url"]` (set programmatically by the
    test `Config`) — **else** `f"sqlite:///{get_settings().app_db_path}"`. **Ignore** any
    `sqlalchemy.url`/`config.get_main_option("sqlalchemy.url")` entirely so a stray `.ini` value cannot
    take effect (round-1 #2). Never reference `baseline.db`.
  - apply `set_sqlite_pragmas` (imported side-effect-free, round-1 #1) so migrations run on a WAL+FK
    connection.
  - standard `run_migrations_offline()` / `run_migrations_online()`, both using `resolve_url()`.
- `alembic/script.py.mako` — new: standard revision template.
- `alembic/versions/0001_initial.py` — new: **empty** `upgrade()` / `downgrade()` (`pass`), the base
  revision (no tables yet — they arrive in E2·P2/P3).
- `tests/database/test_alembic.py` — new: round-trip + target-DB + no-tables assertions on a temp file DB.

## Acceptance

- [ ] **Round-trip on a temp file DB:** programmatic `command.upgrade(cfg, "head")` →
      `command.downgrade(cfg, "base")` → `command.upgrade(cfg, "head")` all succeed (cfg URL pointed at a
      `tmp_path` file via the override).
- [ ] After `upgrade head`, `alembic_version` holds the head revision; after `downgrade base` the
      `alembic_version` table is empty (no version row).
- [ ] **WAL on the migrated file (non-circular):** after `command.upgrade(cfg, "head")` on the temp file
      DB, open that file with a **raw `sqlite3.connect(db_path)`** (NO `set_sqlite_pragmas`, NOT through
      `make_engine`) and `PRAGMA journal_mode` returns `wal` — so the assertion can only pass if `env.py`
      itself attached the listener during the migration (a listener-bearing inspection connection would
      flip WAL on and mask a broken `env.py`) (round-3 #1; round-2 #1; epic R1, §4).
- [ ] **No application tables:** after `upgrade head`, the only table is `alembic_version` (the initial
      migration is empty) — `sqlite_master` lists no app tables.
- [ ] **Targets app.db only:** with no test override, `resolve_url()` equals
      `sqlite:///{settings.app_db_path}` (settings owns it); `grep -rn baseline alembic alembic.ini` finds
      nothing.
- [ ] **Stale `.ini` URL is ignored (negative test):** setting a bogus `sqlalchemy.url` on the `Config`
      does **not** change the target — `resolve_url()` still returns the settings/test-override path
      (round-1 #2).
- [ ] `target_metadata is Base.metadata` (autogenerate would diff against the declarative base).

## Steps

## Notes

`baseline.db` is a **read-only build input** regenerated by `build_db.py` (`DROP TABLE …`) and must never
be opened at runtime or by a migration (DB.md §0; ARCHITECTURE §3) — so Alembic's production URL is derived
from `settings.app_db_path` only (a static `sqlalchemy.url` in `.ini` is ignored, round-1 #2), and the test
grep guards against any `baseline` reference. The only override is an explicit **test-only** channel
(`config.attributes["test_db_url"]`). The pragma helper is imported side-effect-free so loading `env.py`
never builds the runtime engine (round-1 #1). The initial migration is intentionally **empty**: this phase
creates no tables; the nine tables and their R5 constraints land in E2·P2/P3 and will autogenerate against
`Base.metadata` with deterministic names from TASK-002's naming convention (epic §3, §4, §6).
