# Research: E2·P1 — DB engine, WAL & Alembic init

Curated findings only — no raw conversation transcripts. This phase builds the **engine + Alembic
scaffolding + period-key/timestamp helpers** for the runtime database `app.db`. It deliberately creates
**no tables** — the nine tables land in E2·P2 (ingest) and E2·P3 (derived + coaching state).

## Architecture Facts

- **Two databases, split by lifecycle** (DB.md §0; ARCHITECTURE §3): `app.db` is the **only** database the
  running API reads or writes; `baseline.db` is a read-only build input regenerated by `build_db.py`
  (`DROP TABLE …`) and **never opened at runtime**. Durable user state must not live in `baseline.db`.
- **`app.db` is Alembic-owned, WAL, small, backed up, never dropped** (ARCHITECTURE §1 Persistence, §3;
  DB.md §0; epic R1). Backup is `litestream` streaming the WAL to object storage (ARCHITECTURE §1) — so
  WAL must actually be on.
- **WAL mode** (epic R1; DB.md §0): SQLite in WAL journal mode. The standard way under SQLAlchemy is a
  `connect` event listener that issues `PRAGMA journal_mode=WAL` on each new DBAPI connection (and
  `PRAGMA foreign_keys=ON`, since SQLite defaults FK enforcement OFF and E2·P2 adds a FK
  `workout_statistics.workout_id → workouts(id)`).
- **`app.db` = exactly 9 tables, no `profile` table** (epic R3; DB.md §0, §5): constants live in
  `profile.yaml` (E3), not the DB. This phase creates **zero** tables — only the base/metadata that the 9
  tables will attach to later.
- **Timestamps = ISO-8601 TEXT carrying the offset HealthKit emits per sample** (epic R2; DB.md §0;
  ARCHITECTURE §4). The offset **varies** — Europe/Sofia is `+02:00` in winter (EET), `+03:00` in summer
  (EEST), plus travel. Never hard-code `+03:00`. They sort correctly and stay debuggable as TEXT.
- **Period keys (`date`, `iso_week`) via the `Europe/Sofia` tz database** (epic R2; DB.md §0;
  ARCHITECTURE §4): always resolve "today" / "this week" through the tz database (DST-aware), never by
  assuming a fixed offset. `iso_week` format is `YYYY-Www` (e.g. `2026-W23`) — the cache key for
  `plans` and the period key derivation for `suggestions`/`activity_summary`/`daily_metrics` later.
- **Migrations must autogenerate stably** (epic E2·P1 bullet 4): a `naming_convention` on the `MetaData`
  gives deterministic constraint/index names so E2·P2/P3 autogen diffs are clean and the unique
  constraints in epic R5 (`records.uuid`, `workouts.uuid`, `strength_tests.iso_week`, `plans.iso_week`,
  `suggestions.date`) get predictable names.
- **Alembic round-trip is a hard acceptance** (epic §4, §6): `upgrade head` → `downgrade base` →
  `upgrade head` must round-trip cleanly on a temp file DB. The **initial migration may be empty** (no
  tables yet) but the round-trip and the WAL-on-connect must still be testable.

## Constraints

- **Alembic targets `app.db` ONLY** — `env.py` must derive the DB URL from `settings.app_db_path` (or an
  explicit override for tests), and **must never** reference, open, or point at `baseline.db`
  (DB.md §0; epic E2·P1). `baseline.db` is a build input, not a migration target.
- **WAL set via a `connect` event listener** (`PRAGMA journal_mode=WAL`), not a one-off at startup — so
  every pooled connection is in WAL. Verified by querying `PRAGMA journal_mode` on a live connection and
  asserting `wal` (epic R1; runbook §5).
- **No hard-coded offsets** anywhere — period keys go through `zoneinfo.ZoneInfo("Europe/Sofia")`;
  timestamp helpers preserve the offset present on the input string (epic R2; ARCHITECTURE §4).
- **No tables this phase** — out of scope: writing data (E5), computing `daily_metrics` (E6),
  `profile.yaml` (E3), seeding from `baseline.db` (E4), and the 9 table definitions (E2·P2/P3).
- **Dropped stack stays out**: no Postgres/`psycopg`/pgvector, Celery, Redis, Supabase, `vecs`
  (ARCHITECTURE §1 stack note). SQLite + SQLAlchemy + Alembic only.
- **`zoneinfo` tz data must be present.** On some platforms the system tz database is absent; the
  `tzdata` PyPI package is the portable fallback so `ZoneInfo("Europe/Sofia")` resolves in CI/containers.

## Useful Commands

```bash
# build a fresh app.db and round-trip the (initially empty) migration
uv run alembic upgrade head
uv run alembic downgrade base
uv run alembic upgrade head

# confirm WAL is active on a real connection (lazy get_engine — no module-level engine)
uv run python -c "from app.database.engine import get_engine; \
import sqlalchemy as sa; \
print(get_engine().connect().execute(sa.text('PRAGMA journal_mode')).scalar())"  # -> wal

# helper + engine + migration tests
uv run pytest tests/core/test_time.py tests/database -q
uv run ruff check .
```

## Uncertainty

- **Where do period-key helpers live — `app/core/time.py` or `app/database/time.py`?** The runbook allows
  either. Resolved: `app/core/time.py` — period keys are a domain/time concern used by **many** epics
  (E5/E6/E10/E11), not a DB-engine concern; keeping them in `core` avoids importing the DB layer just to
  format a week key. The DB layer (`app/database/`) re-exports nothing from it.
- **Can the initial Alembic migration be empty?** Yes — this phase creates no tables (E2·P2/P3 do). An
  empty initial revision is valid and still exercises the `upgrade`/`downgrade` round-trip and proves the
  Alembic wiring + naming-convention metadata target is sound (epic §4; runbook NOTES).
- **Does WAL persist in the file or per-connection?** `journal_mode=WAL` is a persistent DB-level setting
  once set, but re-issuing it on every `connect` is harmless and guarantees it for fresh files; pairing it
  with `PRAGMA foreign_keys=ON` (which **is** per-connection and OFF by default) is the reason the listener
  is the right home for both.
- **Naming-convention keys.** Resolved to the SQLAlchemy-recommended map (`ix`, `uq`, `ck`, `fk`, `pk`)
  so the E2·P2 FK and the R5 UNIQUE/index names are deterministic across machines.
